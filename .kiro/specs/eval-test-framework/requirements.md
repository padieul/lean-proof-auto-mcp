# Requirements Document: Evaluation Testing Framework

## Introduction

This document specifies requirements for a systematic evaluation testing framework that tests all 6 MCP tools against 23 mathlib fixture files across 7 mathematical domains. The framework replaces ad-hoc single-file investigation with structured per-tool test modules, comprehensive result collection, and tiered execution capabilities. The framework supports both Linux and Windows platforms and operates exclusively within the `tests/lean-proof-auto-mcp-eval_tests/` directory without modifying source code.

## Glossary

- **MCP_Client**: A reusable client component that communicates with the MCP server via JSON-RPC protocol
- **Fixture_File**: A Lean 4 source file from the eval repository containing theorems for testing
- **Result_Collector**: A component that records, persists, and summarizes test execution results
- **Eval_Repository**: The external `lean-proof-auto-mcp-eval` repository containing fixture files
- **Execution_Tier**: A predefined test execution level (smoke, quick, normal, full, deep) with specific time constraints
- **Tool_Result**: A data structure capturing the outcome of a single tool invocation on a theorem
- **Domain**: A mathematical category (Algebra, Analysis, Data, GroupTheory, LinearAlgebra, RingTheory, Topology)
- **Test_Module**: A pytest module containing tests for a specific MCP tool
- **Harness**: A standalone Lean 4 file generated by MCP tools for theorem verification

## Requirements

### Requirement 1: Cross-Platform Path Resolution

**User Story:** As a developer on either Linux or Windows, I want the framework to automatically locate the eval repository, so that I can run tests without manual configuration.

#### Acceptance Criteria

1. WHEN the system runs on Linux, THE Path_Resolver SHALL default to `/home/paul_d/Sources/lean-proof-auto-mcp-eval/`
2. WHEN the system runs on Windows, THE Path_Resolver SHALL default to `C:\Dev\lean-proof-auto-mcp-eval`
3. WHEN the `LEAN_EVAL_REPO` environment variable is set, THE Path_Resolver SHALL use that path instead of platform defaults
4. THE Path_Resolver SHALL use `pathlib.Path` for all path operations
5. WHEN the resolved path does not exist, THE Path_Resolver SHALL raise a descriptive error

### Requirement 2: Reusable MCP Client

**User Story:** As a test developer, I want a reusable MCP client component, so that I can write tests without duplicating server communication logic.

#### Acceptance Criteria

1. THE MCP_Client SHALL support context manager protocol with `__enter__` and `__exit__` methods
2. WHEN entering the context, THE MCP_Client SHALL start the MCP server via `uv run python` command
3. WHEN exiting the context, THE MCP_Client SHALL terminate the server process within 5 seconds
4. THE MCP_Client SHALL provide a `call_tool(name, args)` method that sends JSON-RPC requests
5. WHEN a tool call times out, THE MCP_Client SHALL raise a timeout exception
6. WHEN the server returns malformed JSON, THE MCP_Client SHALL raise a descriptive error
7. THE MCP_Client SHALL provide a `health_check()` method that verifies server responsiveness
8. THE MCP_Client SHALL provide a `restart()` method that terminates and restarts the server

### Requirement 3: Fixture Discovery

**User Story:** As a test developer, I want automatic discovery of all fixture files, so that tests can parametrize over the complete fixture set.

#### Acceptance Criteria

1. THE Fixture_Discovery SHALL enumerate all `.lean` files in the eval repository's `fixtures/mathlib/Fixtures/` directory
2. WHEN discovering fixtures, THE Fixture_Discovery SHALL extract domain from the directory path
3. WHEN discovering fixtures, THE Fixture_Discovery SHALL extract subdomain from the directory path
4. THE Fixture_Discovery SHALL create a `FixtureFile` dataclass for each discovered file containing path, domain, subdomain, and relative_path
5. THE Fixture_Discovery SHALL provide an `ALL_FIXTURE_FILES` constant containing all 23 fixture files
6. WHEN the fixtures directory does not exist, THE Fixture_Discovery SHALL raise a descriptive error
7. THE Fixture_Discovery SHALL discover exactly 23 fixture files across 7 domains

### Requirement 4: Result Collection and Persistence

**User Story:** As a test analyst, I want comprehensive result collection and persistence, so that I can analyze test outcomes and compare against baselines.

#### Acceptance Criteria

1. THE Result_Collector SHALL record each tool invocation with tool name, file path, theorem ID, status, elapsed time, and raw response
2. WHEN recording results, THE Result_Collector SHALL capture timestamps with millisecond precision
3. THE Result_Collector SHALL serialize results to JSON format with proper datetime handling
4. WHEN saving results, THE Result_Collector SHALL create timestamped directories in `reports/`
5. THE Result_Collector SHALL provide a `summary()` method that aggregates results by tool, domain, and status
6. THE Result_Collector SHALL provide a `compare_baseline(baseline_path)` method that compares current results against a baseline
7. WHEN comparing baselines, THE Result_Collector SHALL report regressions, improvements, and unchanged results
8. THE Result_Collector SHALL handle concurrent result recording from parallel test execution

### Requirement 5: Enhanced Pytest Configuration

**User Story:** As a test developer, I want pytest fixtures that provide all necessary test dependencies, so that tests remain clean and focused.

#### Acceptance Criteria

1. THE Pytest_Configuration SHALL provide a session-scoped `eval_repo` fixture that returns the eval repository path
2. THE Pytest_Configuration SHALL provide a session-scoped `mcp_server_path` fixture that returns the server script path
3. THE Pytest_Configuration SHALL provide a session-scoped `result_collector` fixture that persists across all tests
4. THE Pytest_Configuration SHALL provide a module-scoped `mcp_client` fixture that shares a client per test module
5. THE Pytest_Configuration SHALL provide a parametrized `fixture_file` fixture that yields each fixture file
6. THE Pytest_Configuration SHALL register custom markers: `eval_smoke`, `eval_quick`, `eval_normal`, `eval_full`, `eval_deep`
7. THE Pytest_Configuration SHALL register custom markers for each domain: `eval_algebra`, `eval_analysis`, etc.

### Requirement 6: Verify Tool Evaluation

**User Story:** As a test analyst, I want comprehensive testing of the verify tool, so that I can assess its correctness across all fixture files.

#### Acceptance Criteria

1. THE Verify_Test_Module SHALL test the verify tool on all 23 fixture files
2. WHEN testing verify, THE Verify_Test_Module SHALL validate that the tool returns a valid response structure
3. WHEN verify succeeds, THE Verify_Test_Module SHALL record the result with status "success"
4. WHEN verify fails, THE Verify_Test_Module SHALL record the result with status "failure" and error details
5. THE Verify_Test_Module SHALL mark tests with appropriate tier markers (smoke tests for 2 files, quick for 5 files, normal for all)

### Requirement 7: Probe Tool Evaluation

**User Story:** As a test analyst, I want comprehensive testing of the probe tool across all theorems and modes, so that I can assess its behavior on individual theorems.

#### Acceptance Criteria

1. THE Probe_Test_Module SHALL test the probe tool on theorems from all 23 fixture files
2. THE Probe_Test_Module SHALL test each theorem in all three modes: `aesop`, `grind`, `both`
3. WHEN testing probe, THE Probe_Test_Module SHALL validate the response contains theorem information
4. THE Probe_Test_Module SHALL record results for each theorem-mode combination
5. THE Probe_Test_Module SHALL mark smoke tier tests to cover 2 files with 5 theorems each in one mode
6. THE Probe_Test_Module SHALL mark quick tier tests to cover 5 files with 10 theorems each in all modes

### Requirement 8: Probe File Tool Evaluation

**User Story:** As a test analyst, I want comprehensive testing of the probe_file tool, so that I can assess its file-level analysis capabilities.

#### Acceptance Criteria

1. THE Probe_File_Test_Module SHALL test the probe_file tool on all 23 fixture files
2. THE Probe_File_Test_Module SHALL test each file in all three modes: `aesop`, `grind`, `both`
3. WHEN testing probe_file, THE Probe_File_Test_Module SHALL validate the response contains a list of theorems
4. THE Probe_File_Test_Module SHALL verify that returned theorem counts match expected ranges
5. THE Probe_File_Test_Module SHALL mark smoke tier tests for 2 files in one mode
6. THE Probe_File_Test_Module SHALL mark quick tier tests for 5 files in all modes

### Requirement 9: Automated Proof Tool Evaluation

**User Story:** As a test analyst, I want testing of automated proof tools on selected theorems, so that I can assess their proof-finding capabilities.

#### Acceptance Criteria

1. THE Automated_Proof_Test_Module SHALL test `search_automated_proof` on selected theorems from each domain
2. THE Automated_Proof_Test_Module SHALL test `try_automated_proof` on validation cases
3. WHEN testing automated proof tools, THE Automated_Proof_Test_Module SHALL record proof success or failure
4. WHEN a proof is found, THE Automated_Proof_Test_Module SHALL record the proof tactic
5. THE Automated_Proof_Test_Module SHALL mark all automated proof tests as normal tier or higher

### Requirement 10: Context Tool Evaluation

**User Story:** As a test analyst, I want testing of the get_proof_context tool, so that I can assess context extraction quality.

#### Acceptance Criteria

1. THE Context_Test_Module SHALL test `get_proof_context` on theorems from all domains
2. WHEN testing get_proof_context, THE Context_Test_Module SHALL validate the response contains relevant context
3. THE Context_Test_Module SHALL verify that context includes imports, definitions, and related theorems
4. THE Context_Test_Module SHALL record context quality metrics (completeness, relevance)

### Requirement 11: Cross-Tool Consistency Validation

**User Story:** As a test analyst, I want validation that tools agree on theorem existence, so that I can identify inconsistencies in tool behavior.

#### Acceptance Criteria

1. THE Cross_Tool_Test_Module SHALL verify that probe and verify tools agree on which theorems exist in a file
2. WHEN tools disagree on theorem existence, THE Cross_Tool_Test_Module SHALL record the discrepancy
3. THE Cross_Tool_Test_Module SHALL test consistency across at least 5 fixture files
4. THE Cross_Tool_Test_Module SHALL mark consistency tests as normal tier

### Requirement 12: Domain Coverage Reporting

**User Story:** As a test analyst, I want per-domain aggregation of results, so that I can identify domain-specific issues.

#### Acceptance Criteria

1. THE Domain_Coverage_Module SHALL aggregate results by mathematical domain
2. THE Domain_Coverage_Module SHALL report success rates per domain per tool
3. THE Domain_Coverage_Module SHALL identify domains with below-threshold success rates
4. THE Domain_Coverage_Module SHALL generate domain coverage reports in JSON format

### Requirement 13: Tiered Execution Scripts

**User Story:** As a developer, I want execution scripts that support different test tiers, so that I can run appropriate test suites for my workflow.

#### Acceptance Criteria

1. THE Execution_Scripts SHALL provide `run_eval.sh` for Linux/macOS
2. THE Execution_Scripts SHALL provide `run_eval.bat` for Windows
3. WHEN invoked with `smoke` tier, THE Execution_Scripts SHALL complete in under 2 minutes
4. WHEN invoked with `quick` tier, THE Execution_Scripts SHALL complete in under 10 minutes
5. WHEN invoked with `normal` tier, THE Execution_Scripts SHALL complete in under 30 minutes
6. WHEN invoked with `full` tier, THE Execution_Scripts SHALL complete in under 2 hours
7. WHEN invoked with `deep` tier, THE Execution_Scripts SHALL run all tests regardless of duration
8. THE Execution_Scripts SHALL create timestamped result directories in `reports/`
9. THE Execution_Scripts SHALL support the `LEAN_EVAL_REPO` environment variable
10. WHEN no tier is specified, THE Execution_Scripts SHALL default to `normal` tier

### Requirement 14: Result Directory Management

**User Story:** As a test analyst, I want organized result storage, so that I can track test runs over time.

#### Acceptance Criteria

1. THE Result_Manager SHALL create a `reports/` directory if it does not exist
2. WHEN saving results, THE Result_Manager SHALL create subdirectories named `eval-YYYYMMDD-HHMMSS-{tier}/`
3. THE Result_Manager SHALL save a `summary.json` file in each result directory
4. THE Result_Manager SHALL save detailed results in `results.json` in each result directory
5. THE Result_Manager SHALL save execution metadata (tier, duration, platform) in `metadata.json`

### Requirement 15: Documentation and Usage

**User Story:** As a new developer, I want clear documentation on running the evaluation framework, so that I can use it effectively.

#### Acceptance Criteria

1. THE Documentation SHALL provide a README.md in the eval tests directory
2. THE Documentation SHALL explain all five execution tiers with example commands
3. THE Documentation SHALL document cross-platform path configuration
4. THE Documentation SHALL provide examples of running specific test modules
5. THE Documentation SHALL explain how to interpret result files
6. THE Documentation SHALL document the `LEAN_EVAL_REPO` environment variable

### Requirement 16: Isolation from Existing Tests

**User Story:** As a developer, I want the evaluation framework to not impact existing tests, so that I can maintain CI/CD stability.

#### Acceptance Criteria

1. THE Evaluation_Framework SHALL reside exclusively in `tests/lean-proof-auto-mcp-eval_tests/`
2. THE Evaluation_Framework SHALL not modify any files in `src/`
3. THE Evaluation_Framework SHALL use distinct pytest markers that are excluded from CI/CD
4. WHEN running the standard test suite, THE Evaluation_Framework tests SHALL not execute
5. THE Evaluation_Framework SHALL not interfere with existing test fixtures or configuration
